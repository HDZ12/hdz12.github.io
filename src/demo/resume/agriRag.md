## 设计并实现长文档“多级分块 + 父子索引”机制，基于递归分块与 Overlap 构建父块，结合语义分块生成细粒度子块，并使用 Qwen-Embedding 完成向量化；检索命中子块后回溯父块恢复上下文，缓解长文档语义割裂问题。
父块按照2048去切，子块按照512去切，只向量化子块，父块存在数据库里。父子全做overleap。检索的时候只命中子块，去数据库查关联的父块。加入上下文。

切分优先级都是：
  段落边界
  → 句子边界
  → HanLP 词边界
  → 字符兜底

整体两级切分

  解析后的完整文本
      ↓
  按约2048字符生成父块
      ↓
  父块写入 parent_chunks
      ↓
  每个父块内部按约512字符生成子块
      ↓
  子块写入 document_vectors
      ↓
  只对子块做Embedding并写入ES

  父块和子块使用同一个切分方法，只是目标大小不同：

  父块目标：2048字符
  子块目标：512字符
  最小块：100字符
  Overlap：最多100字符

  其中 2048、512 都是软目标。

  ———

  ### 二、第一步：按段落切分

  程序优先把连续空行当作段落边界：

  text.split("\n\n+")

  例如：

  第一段内容……

  第二段内容……

  第三段内容……

  会先得到三个段落。

  #### 多个段落能放进目标块

  假设生成子块，目标是 512：

  第一段：180字符
  第二段：220字符
  第三段：200字符

  程序依次累积：

  第一段 + 第二段 = 402字符

  不超过 512，所以放在同一个子块。

  再放第三段：

  402 + 2个换行符 + 200 = 604字符

  超过 512，所以结果是：

  子块1：第一段 + 第二段
  子块2：第三段

  因此，一个子块可以包含多个完整段落。

  ———

  ### 三、第二步：长段落按句子切分

  如果单个段落本身已经超过目标大小，就不能整体放入一个块。

  例如：

  一个段落长度为900字符
  子块目标为512字符

  程序会根据中英文标点切成句子：

  。 ！ ？ ；
  . ! ? ;

  例如：

  句子A：200字符
  句子B：180字符
  句子C：240字符
  句子D：150字符

  累积结果：

  A + B = 380字符

  继续加入 C 会超过 512，所以：

  子块1：A + B
  子块2：C + D

  原则是优先保留完整句子，不在第 512 个字符处机械切断。

  ———

  ### 四、第三步：超长句子按 HanLP 词边界切分

  如果单个句子也超过 512，例如一大段没有标点的 OCR 文本：

  这是一个非常非常长并且没有任何标点符号的中文句子……

  程序使用 HanLP 分词：

  这是 / 一个 / 非常 / 长 / 没有 / 标点 / 的 / 中文 / 句子

  然后按词依次累积。

  如果再加入下一个词会超过目标大小，则生成新块：

  子块1：词1……词N
  子块2：词N+1……

  这样能尽量避免从中文词语中间切断。

  ———

  ### 五、第四步：字符切分兜底

  如果 HanLP 分词失败，程序最后会按字符强制切分：

  每达到约512字符就生成一个块

  这是兜底措施，保证以下极端文本也能处理：

  - 没有标点的超长文本
  - OCR 产生的异常文本
  - HanLP 无法正常处理的内容
  - 特殊符号连续文本

  所以切分优先级是：

  段落
  → 句子
  → HanLP词边界
  → 字符强制切分

  ———

短块合并

  基础切分完成后，如果当前块或前一个块小于 100 字符，就尝试合并：

  if ((当前块长度 < 100 || 前块长度 < 100)
          && 合并后长度 <= 512 + 100) {
      前块 = 前块 + "\n\n" + 当前块;
  }

  例如：

  前块：430字符
  当前块：60字符
  合并后：492字符
  → 可以合并

  前块：540字符
  当前块：80字符
  合并后：622字符
  → 超过612，不合并

  如果第一个块很短，则处理下一个块时，也可能把第一个短块和第二个块合并。因此短块既可能被并入前块，也可能通过下一轮与
  后块组合。

Overlap 算不算在 512 里面？

  不算。

  执行顺序是：

  先生成目标约512的基础块
  → 短块合并
  → 再把前一块尾部最多100字符加到下一块开头

  例如：

  子块1：500字符
  子块2原文：480字符

  从子块1尾部取100字符
  → 子块2最终约580字符

  所以 512 是不包含 Overlap 的基础目标大小。

  而且短块合并发生在 Overlap 之前，因此极端情况下：

  短块合并后的基础块：最多约612字符
  再加入100字符Overlap
  最终可能约714字符

  再考虑不可拆分的特殊长词，理论上还可能略大。所以不能把 612 当成严格上限。

PDF 的特殊规则

  PDF 先按页解析：

  第1页
  → 生成该页父块
  → 生成该页子块

  第2页
  → 生成该页父块
  → 生成该页子块

  当前不会把第1页和第2页直接合成同一个父块。

  每个父块和子块还会记录：

  pageNumber
  anchorText

  用于回答引用时定位 PDF 页码。

## 搭建基于 Kafka 的异步文档处理流水线，完成文件上传、Java ETL 解析与向量化入库的流程解耦，提升系统吞吐与任务处理稳定性；针对大文件场景引入分片上传、断点续传及 Redis BitMap 分片状态管理，将 100MB 文件上传耗时从 7.7s 降低至 2.5s。
**Kafka 异步文档处理**：
文件上传和合并完成
->生产FileProcessingTask
->kafka保存任务
->Consumer异步消费
->下载MinIo文件
->java解析
->文本分块
->Embedding
->ES入库

```info
  ETL
  Extract：Tika/LiteParse 从 Word、PDF、TXT 提取文本
  Transform：清洗、语义分块、Overlap、补充权限与页码元数据
  Load：写 MySQL，生成向量，再写 Elasticsearch
```

### 当一个文件最终合并成功，并准备在数据库中创建它的元数据记录时（在`file_upload`表中），你是如何确定并记录这个文件的权限归属的？比如，系统如何知道这个文件是‘王二’上传的？除了记录所有者，有没有机制允许上传者为这个文件指定一些‘组织标签’（比如，‘仅自己可见’或‘研发部可见’）？"
所有权确定，基于JWT做身份认证，所有接口，分片上传，合并操作，前端必须带上JWT。这个token再被后端拦截解析之后，提取出userid。第一次上传分片时，相关信息直接写入数据库。
合并文件这种敏感操作，系统要再做权限校验，通过fileMD5+userid取数据库查这个文件记录。确认这个操作时用户发起的，防止用户合并别人文件。访问权限用组织标签实现。
### 为什么最终选择了Kafka来实现异步处理？相比于其他消息队列（如RabbitMQ），它有什么优势？
1.文件上传后，会有后续很多的异步任务，比如元数据提取，生成全文索引，文本向量化。这些处理不仅数据量大，而且本身也消耗资源，属于典型的流式处理场景。
2.kafka本身适合高吞吐的数据流，他的架构决定了他可以每秒处理百万条数据。而且他是基于磁盘顺序写入，非常稳定。根RabbitMQ那种内存优先，消息读完即删的机制不一样。kafka消息保存再磁盘上，数据持久化能力比较强。保留久，用offset控制消费进度。可以随时进行数据回溯。
比如某个向量化模型升级了，或者数据处理逻辑修复了 bug，我们只需要新建一个消费组从历史 offset 开始消费，就能批量重跑所有老的文件数据，不用动数据库。
### 在使用Kafka时，你是如何配置来确保消息的可靠传递的
**生产者**: 配置acks=all，生产者发送一条信息，必须等所有同步副本全部写成功，才认为消息发出成功了。kafaka最高等级的可靠性设置，哪怕leader写完宕机了，只要follwer写成功了，就不影响落盘。
**服务端**: 把每个topic的副本数设置为3，一个leader+2个follower，配置min.insync.replicas=2。当只有一个副本存活时，broker拒绝写入。
**消费者**:我们没有用 Kafka 默认的自动提交，而是设置了 ｅｎａｂｌｅ．ａｕｔｏ．ｃｏｍｍｉｔ=false 转为手动提交。这样能确保只有当我们的业务逻辑真正执行成功，比如向量写入 ES 成功，数据库状态更新成功，才会调用 commitSync() 提交 offset。这样即使系统崩溃，重启后还能从失败点重新拉取任务，保证至少处理一次，不会丢任务。
### kafka怎么保证消息重试
**生产者** 容易实现，配置重试次数为3.
**消费者**:DefaultErrorHandler 实现了一套优雅的消费者重试与死信队列机制。FixedBackOff 会阻塞当前消费线程 ，等待 1 秒后进行第一次重试。如果再次失败，它会再等 1 秒，进行第二次重试，总共最多重试 4 次。如果 4 次后仍然失败， DeadLetterPublishingRecoverer 会接管这个消息，将它发送到死信队列中 （在项目中是 file-processing-dlt ）
### 在文档解析过程中，你是如何处理不同格式（PDF、Word、txt）的文档的？遇到的最棘手的技术难点是什么？"
我们采用了开源工具 Apache Tika 来完成文档的解析工作。其核心组件 AutoDetectParser 能够自动识别上传文件的类型（如 PDF、Word、txt 等），并统一提取纯文本内容。尽管 Tika 功能强大，但仍然存在不足。比如无法处理扫描件类型的 PDF，这类文档不包含可提取的文本信息，下个版本我们打算集成 Tesseract OCR 引擎来完成。
